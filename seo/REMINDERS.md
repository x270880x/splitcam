## 2026-09-06 — мёртвые адреса: проверка подключена к Search Console

`seo/linkcheck.py` видит только ссылки ВНУТРИ сайта. Адреса, которые Google до сих пор показывает
людям, а сервер отвечает 404, он не видит принципиально. Теперь это отдельный инструмент:

```bash
python3 seo/deadlinks.py              # 90 дней, адреса с показами ≥5
python3 seo/deadlinks.py --min 1 --days 28 --json out.json
```

Берёт из консоли все адреса с показами, дёргает каждый на живом сайте и отдельно проверяет, КУДА
ведёт перенаправление: 301 на несуществующую страницу выглядит здоровым в любом отчёте, а для
человека это тот же тупик.

## 2026-09-07 — отправка адресов в поисковики

```bash
python3 seo/indexnow.py --new        # страницы, созданные за 14 дней
python3 seo/indexnow.py --all        # все адреса из sitemap.xml
python3 seo/indexnow.py --all --dry  # посмотреть без отправки
```

**IndexNow — Bing, Yandex, Seznam, Naver.** Ключ уже лежит на хосте
(`/485c229ee85ee55f1967363aabec7e9a.txt`, вне git, host-managed) и проверяется скриптом ПЕРЕД
отправкой: без ключа приёмная сторона отклоняет список молча. Первая отправка 2026-09-07: все
877 адресов из карты, ответ HTTP 200. Отправляли всю карту, а не только новые страницы, потому что
за 05–06 сентября изменились 984 страницы — заголовки, описания, крошки, FAQ, перелинковка.

🔴 **Google в IndexNow не участвует, и отправить туда страницу программно нельзя.** Indexing API
принимает только вакансии и трансляции; наш служебный аккаунт вдобавок имеет доступ только на
чтение (`webmasters.readonly`). У Google два пути, оба уже работают или требуют рук:
- карта сайта зарегистрирована (`sitemaps.list`: одна карта, 0 ошибок, последнее чтение
  2026-09-03) и перечитывается сама; с 2026-09-06 у каждой строки честная дата изменения,

### Побочная находка: `Disallow: /v2/` не работал

Проверка robots.txt при этой же отправке показала, что запрет архива не действовал, и по двум
причинам сразу. Во-первых, он стоял ПОСЛЕ пустой строки, а пустая строка завершает запись — такая
директива не принадлежит никакому user-agent и молча игнорируется. Во-вторых, даже внутри записи он
стоял ниже `Allow: /`: Google берёт самое длинное совпадение и запрет бы применил, а разборщики,
берущие первое совпадение (в том числе `urllib.robotparser`), выбрали бы `Allow`. Теперь `Disallow`
стоит ВЫШЕ `Allow`, что верно при обеих трактовках; проверено на восьми адресах.

Практического вреда не было: `/v2/` вообще не выкладывается (деплой его исключает, живой адрес
отдаёт 404), у локальной копии стоит `noindex`, и за 90 дней у неё ноль показов. Но правило было
декоративным, а выглядело работающим.

⚠️ И отдельная ловушка проверки: `urllib.robotparser.read()` при неудачной загрузке НЕ бросает
исключение, а оставляет пустой набор правил, после чего `can_fetch` возвращает False на всё. Это
дало ложную тревогу «все новые страницы запрещены». Разбирать нужно уже скачанный текст через
`parse()`, а не доверять его собственной загрузке.


## 2026-09-17 — восстановлен /auth (возврат OAuth в мобильное приложение)

После редизайна маршрут пропал: `/auth` отдавал 404, и в Android-приложении ломался вход через
Twitch и Kick. Провайдер присылает браузер на `https://splitcam.com/auth?code=…&state=…`, страница
обязана вернуть пользователя в приложение по схеме `splitcam://auth` с ТЕМИ ЖЕ параметрами.

**Страница лежит ФАЙЛОМ `/auth.html`, а не каталогом `/auth/index.html`. Это принципиально.**
Пока это был каталог, `mod_dir` (DirectorySlash) срабатывал РАНЬШЕ mod_rewrite и отдавал 301 на
`/auth/` — лишний хоп посреди OAuth-обмена. К файлу добавлять слеш не к чему, и ответ сразу 200.

Правило в `seo/redirects.htaccess`, сразу после `RewriteEngine On`:
`RewriteRule ^(?:[a-z]{2,3}/)?auth/?$ /auth.html [L,QSA]` — QSA сохраняет query как есть, префикс
локали тоже принимается. Заголовки «не кэшировать» — через `<Files "auth.html">`.

### Три грабли, на которые наступили по дороге

1. **`RewriteRule` попал в комментарии ДО `RewriteEngine On` и молча не работал.** В файле фраза
   «canonical URL form: strip trailing slash» встречается дважды — в пояснении в шапке и в самом
   блоке внизу. Поиск по первому вхождению вставил правило в мёртвую зону. **Вставляя правило,
   проверять номер строки против `RewriteEngine On`.**
2. **`<If "%{REQUEST_URI} =~ …">` на этом хосте не работает.** LiteSpeed игнорирует условный блок
   молча: оригин отдавал ответ вообще без `Cache-Control`. `<Files>` исполняется.
3. **LiteSpeed кэширует и 404.** После правки адрес несколько минут продолжал отдавать старый
   ответ. Проверять с уникальным query, иначе легко решить, что правка не сработала.

### Кэш Cloudflare — остаток, который НЕ закрыт

Правило страницы `*splitcam.com/*` (`cache_everything`, edge и browser TTL 86400) кэширует весь
сайт на сутки и перекрывает заголовки оригина. Исключение для `/auth` добавить не удалось:
- page rules — лимит 3 на бесплатном тарифе, все заняты (`/forum/*`, `/wp-*/*`, `/*`);
- cache rules — оператор `matches` требует Business; а `PUT` в набор ЗАМЕНЯЕТ его целиком, а там
  7 рабочих правил, включая `ver.txt` и установщик. 🔴 **Не делать `PUT` в
  `rulesets/phases/http_request_cache_settings/entrypoint`, не приложив все существующие правила.**

Практически это безвредно: тело страницы одинаково при любом query, а адрес возврата вычисляется
в браузере из `location.search`. Опасен был только закэшированный 404 — он сброшен.
Если понадобится закрыть насовсем: освободить одно page rule (кандидат — `/wp-*/*`, WordPress
давно снесён) и завести `*splitcam.com/auth*` → `cache_level=bypass` с приоритетом выше `/*`.

Проверка: `curl -sI 'https://splitcam.com/auth?code=x&state=y' | head -1` → 200,
в теле есть `splitcam://auth`. `/.well-known/assetlinks.json` не трогался — 200, application/json.

## Если Python-скрипты падают с `gaierror` / `Unable to find the server` (2026-08-24)

Симптом: `gsc.py`, `tester_signups.py`, `vc_cluster.py` падают на разрешении имён, при этом
`curl` до тех же хостов работает. Из Python не резолвится **ничего**, даже `splitcam.com`.

Причина — не Python. Mac сидит на **точке доступа телефона** (`192.168.49.x`), а она:
- отвечает по DNS, но на все запросы даёт `REFUSED` → прямого DNS нет вообще;
- пропускает трафик только через HTTP-прокси `192.168.49.1:8181`.

`curl` работает, потому что читает `HTTP_PROXY`/`HTTPS_PROXY` из окружения и отдаёт имя прокси.
`socket.getaddrinfo()` в Python так не умеет — он резолвит сам и упирается в `REFUSED`.

**Лечение (одно из двух):**
1. Перейти на обычную сеть — тогда всё работает без правок. Это предпочтительно.
2. Остаться на точке доступа: в окружении `.gscvenv` должен стоять **`pysocks`**, иначе
   `httplib2.socks is None` и httplib2 молча игнорирует прокси, даже увидев его.
   Поставлено 2026-08-24. Запускать так:
   ```bash
   export http_proxy=http://192.168.49.1:8181
   export https_proxy=http://192.168.49.1:8181
   seo/.gscvenv/bin/python seo/gsc.py --days 7
   ```
   ⚠️ Переменные нужны в **нижнем** регистре — httplib2 читает только их.

⚠️ Отдельная поломка того же происхождения: у `seo/.gscvenv/bin/pip` в shebang остался
**старый путь проекта** (`Documents/Дизайны/SplitCam/SPLITCAM DEV./…`) с переезда папки, и он
не запускается. Ставить пакеты через `seo/.gscvenv/bin/python -m pip install …`, либо
пересоздать окружение.

## 🔴 Правило: никогда не редиректить с явного `/<locale>/` URL

_Как выяснилось (2026-07-18): собственный JS де-индексировал 512 локализованных страниц._
The 512 locale pages (97% of the 526-URL sitemap) were **not indexed**, and it was NOT crawl
latency. The `<!--AD-->` language auto-redirect ran on EVERY page, including explicit `/xx/` URLs:
on `/ru/features` it compared `document.documentElement.lang` ("ru") against the browser language
and, for any English-language client, did `location.replace('/features')`. **Googlebot crawls with
`en-US`**, so Google was bounced off every localized page onto its English twin and never indexed
them. **Fix:** the redirect now only fires on URLs WITHOUT an explicit locale prefix — an explicit
`/xx/` URL is always respected; a foreign visitor landing on an English page is still forwarded, so
the UX intent survives. Verified 9/9 scenarios in node. Applied to all 526 pages **and to
`seo/i18n.py`** (the generator) so `i18n_wire.py` can't reintroduce it.
**Standing rule: never auto-redirect away from an explicit `/<locale>/` URL.**
